Overview

Doodle Room started as something small and practical. I wanted a whiteboard my friends and I could all draw on at once, mostly for taking shared notes and doodling during class instead of passing a notebook around. I built the backend in Java on top of Java-WebSocket and kept the frontend as plain HTML5 canvas and vanilla JavaScript, with no framework and no build step, so it was just something I could open in a tab and use immediately.

Once the free-draw part actually worked and people were using it, I kept wanting to add "just one more thing." First cursor tracking, then a skribbl.io-style guessing game on top of the same drawing primitives. That game mode ended up being the bigger half of the project, a full turn-based Pictionary implementation with room codes, scoring, and hint timing. It runs as a second, independent server, so I never had to touch the free-draw mode to build it.

Design & Implementation

Two servers, on purpose. Free Draw and Pictionary are genuinely different problems. One just relays draw events to everyone in the room, and the other needs a real state machine with authority over turns, timers, and scoring. Rather than cram both into one increasingly tangled server, I split them into WhiteboardServer on port 8080 and PictionaryServer on port 8081, sharing only the same Maven build. That meant I could build and break the game mode freely without any risk of regressing the free-draw mode people were already using.

The game is a real state machine. Each room moves through LOBBY → PICKING_WORD → DRAWING → TURN_END and back around for the next turn, then GAME_OVER once the rounds run out. Every scheduled callback, whether it's the per-second timer tick, the letter reveals, or the auto-pick-a-word timeout, captures a "turn token" and re-checks it before acting, so a stray timer firing after a turn has already ended can't corrupt the next one. That defensive detail came directly out of thinking through what happens when a drawer disconnects mid-turn, the kind of edge case that's easy to skip until you actually trace through what a late timer callback would do.

Guess evaluation, not just string matching. An exact match is the easy case. What I actually spent time on was the near-miss. A guess exactly one Levenshtein edit away from the answer gets flagged as "so close!" instead of silently failing, which matters a lot more for how the game actually feels than the happy path does. Scoring follows the same instinct, since earlier and faster correct guesses are worth more (max(20, 100 − 20×priorGuessers) + min(30, secondsLeft/2)), and the drawer gets a flat bonus per correct guesser, so drawing well is worth something too, not just guessing well.

Letting late joiners catch up. The server keeps a bounded history of recent stroke events and replays it to anyone who connects mid-session, so joining a room in progress shows the actual canvas instead of a blank one. It's a small thing, but it's the difference between the whiteboard feeling like a shared document and feeling like you missed something.
